## 背景

方案 §6.1 预检、§6.2 候选生成、§6.3 语义理解、§10.1 面向 Agent 的设计原则、§14.1 与 §14.2（示例图的预检和切分规划）。`CONTEXT.md` 的“分析产物”“输入”两节。

## 要做的事

### 1. `ui-pro analyze`

- 选界面（`ctx.requireScreen`）。界面里已经有根以外的节点时拒绝，错误码 `E_ALREADY_ANALYZED`，提示用 `ui-pro history undo` 撤销上次分析。`--update`（源文件更新后保留已有工作的重新分析，§6.9）先注册成选项，使用时返回 `E_NOT_IMPLEMENTED`。
- 按 `screen.source.kind` 分派：`flat` 调 `analyzeFlatScreen`，`psd` 调 `@ui-pro/psd` 的 `analyzePsdScreen`（工单 03 实现，现在是占位，签名不会变）。
- 选项 `--allow-degraded`、`--dry-run` 原样传进 `AnalyzeOptions`。
- 响应：`summary` 用一句话说明结果和风险，`data` 是 `AnalysisReport`，`views` 是看图的路径，`ask` 和 `warnings` 透传，`next` 给出下一步（看图、撤销）。

### 2. `analyzeFlatScreen`

**预检**：放大倍数就是 `screen.scale`。超过 1.5 倍时按 §14.1 的口径列为风险；JPEG 源文件提示压缩痕迹。截图杂质（例如示例图左侧那两个圆形“<”箭头）的自动识别不强求，做得到就以 `ask` 请用户确认是否排除。

**候选**，坐标一律是源文件像素：

- 传统图像算法：用 opencv（`loadOpenCv()`）做边缘、轮廓、连通域、圆角矩形检测。游戏 UI 背景花哨，需要多尺度或多阈值，按 IoU 去重。候选之间的包含关系写进 `parent`。
- 文字识别：`@gutenye/ocr-node`。已知的三个问题必须处理（实测见 `../ref/ocr/`）：
  1. 坐标在缩放后的空间，要换算回源文件像素。
  2. 小字漏检：原图只认出 1 个“+5”，放大 2 倍后 4 个，3 倍后 5 个（共 6 个）。在多个尺度上识别并合并。
  3. 整行合并：`+5 糖果骑士 +5`、`攻击 3,260` 被合成一个框。在行框内按墨迹的列投影找大间隙，把它拆开，再分别识别或按间隙分配文字，让每段文字有自己的框。
- 自相似：找出重复出现的图形，聚成 `kind: 'visual'` 的相似簇。它是“同形同判”的数据基础。装备框的底色不同（紫、黄、蓝、橙、绿），结构相同，所以相似度要对颜色不敏感（例如比较灰度边缘）。
- 候选 id `cand#<n>`，按位置稳定排序，同样的输入得到同样的编号。

分割模型（§6.2 第一条）不在这一批，但候选的来源要设计成可以再加一种。mask 留到第 3 批的资产构建，这一批只给框。

**草稿**（§6.3）：用启发式规则生成一批 `node.add`：

- 文字候选成为文字节点，带 `text.content`。纯数字、带千分位或 `Lv.` 这类的内容设 `text.kind: 'value'`。
- 包含关系成为层级。
- 同一个相似簇的候选各自成为节点，`from` 指向它们，`cluster` 会自动继承。
- id 省略，由内核编号；角色不确定时不填，留给 Agent。

**提交**：`applyOps(project, ops, { screen, evidence: { [screen]: { candidates } }, message })`，证据和草稿在同一个版本里。`dryRun` 时传 `dryRun: true`，什么都不写。提交后生成一张概览看图，放进 `views`。

### 3. `ui-pro look`

§6.3：“CLI 把候选区域编号后叠在基准图上输出，先给全图概览，再按区域给放大图，保证红点这类小元素也看得清。”

- 底图一律取 `referenceImagePath(screen)`，所以 PSD 界面也能看。
- 概览：基准图放大到能看清的尺寸，叠加框和标签。节点标 id；候选标编号（`cand#47` 标成 `47`）。来源不同用不同颜色。标签尽量不互相遮挡。
- `look <目标>`：目标是选择器（节点）或 `cand#n`，输出带上下文边距的放大图，图里的其他框也标出来。
- 小元素多时，除概览外自动给几张分区放大图。
- 选项至少有：只看节点或只看候选、放大倍数。
- 输出到 `.ui-pro/look/`（`scratchPath`），不进历史。`views` 返回绝对路径（正斜杠）；`data` 里给图例：标签 → id、源文件像素框和设计像素框。
- 标签只用 ASCII，避免字体问题。

#### 需要父 agent 决定 / 知道的

- **草稿节点用显式 id**（`<类型>_<序号>`，如 `container_3`、`text_12`），没有省略 id。原因：同一批 `node.add` 里的子节点要用 `parent: '#<id>'` 指向刚加的父节点，选择器查不到证据里的候选，所以只能先定 id；序号会避开界面里已有的 id。工单写的是“id 省略”，这是偏离。
- **草稿范围**：所有文字都进草稿；形状候选只有“属于某个相似簇”或“里面有文字”的才进，节点类型按有无已入草稿的子节点分 `container` / `image`；角色一律留空给 Agent。
- **相似簇 id 是 `vis#<n>`**，`kind: 'visual'`；文字按“同字同大小”成簇，形状按边缘轮廓成簇（对颜色不敏感，有轮廓剖面惩罚、大小门限、不重叠要求）。
- **整行拆分的做法与工单不同**：工单建议按列投影找间隙，实测在花哨背景上得到的是垃圾；改成把行裁出来、放大并旋转 ±12° 后让 OCR 重读，仅当重读结果拼起来与整行文字完全相同、且至少 2 段时才采用，否则保留整行。
- **`--dry-run` 的 `views` 是空数组**（预演不写任何文件，包括看图）。
- **看图的标签用 SVG 文字渲染（Arial / sans-serif），依赖系统字体**；本机正常，没有任何无衬线字体的机器上标签可能显示空白或方块。
- **OCR 模型只在进程内加载一次**（模块级共享 Promise），冷启动只比热启动多约 0.3 秒；`analyze` 里文字占大头，尺度已经从 1/2/3/4 倍降到 1/2/4 倍来压时间。
- 对非自己文件的修改请求：**没有**。
